## Known limitations

- 0.1.0 is a release candidate; Linux/macOS and Python 3.11 CI have not run here.
- Mutation rules follow the editor: `@tool`-script nodes need `allow_tool_script`; instance internals need editable children and nested-instance internals stay read-only; inherited nodes take overrides only.
- Inherited detection reads the saved scene file (`get_scene_inherited_state()` is not exposed to GDScript): if a base file changes after the scene was opened every node is treated as inherited until the scene is reopened.
- Script variables, allowlisted engine properties and resource sub-properties are type-checked and checked against the inspector's range, enum, flags and layer hints (a layer mask must be non-negative, all layers is 4294967295, not -1; `radians_as_degrees` ranges compare in radians); `runtime.set_property` shares the check. Only scalar, vector, color, NodePath and simple-resource values are encodable. No cross-command atomic transaction API.
- Reparent keeps the global pose for Node3D, Node2D and Control (a Control only its global position; into a Container the Container decides the layout, as in the editor) and undo restores the raw local pose. Engine tests cover Node3D, Node2D and a Control under a Container; the Control pivot offset compensation, a Node2D under a Control parent and a Control under a Node2D parent are not covered. `node.set_transform` is Node3D-only and honours `rotation_order`; a position-only edit keeps the basis, a rotation or scale argument drops shear, and a `--world` rotation or scale under a rotated, non-uniformly scaled parent stays lossy. `describe()`/`node.inspect` expose Node3D data only, so 2D and UI transforms are readable through `node.get_property` (position, rotation, scale) but not through `node.inspect`.
- `node.instantiate` loads the scene with `CACHE_MODE_IGNORE`, so its own sub-resources come fresh from disk. Sub-resources of nested instanced scenes and shared external resources (`.tres`, textures, scripts) still come from the engine's resource cache (`CACHE_MODE_IGNORE_DEEP` was rejected because it reloads cached scripts in place), so a reopen or reimport is needed for those; whether a graphical editor's focus-in rescan changes this was not observed. Instantiating a scene whose embedded script has `extends "res://scripts/x.gd"` logs one `Resource file not found: res://scenes/<scene>.tscn::<id> (expected type: Script)` error in the editor log (not seen with `CACHE_MODE_REUSE`); the script still works and its own and inherited exports read correctly, so it looks cosmetic, but it was not investigated further.
- The `@tool` opt-in screen of `node.instantiate` fails closed and now covers GDScripts embedded in scene files (a pre-load text screen of `.tscn`/`.tres` plus a state walk of node scripts in every closure scene, instance overrides and base chains included), but it is incomplete: embedded Resource scripts inside binary `.scn`/`.res` files are not text-screened (only node scripts in `.scn` are caught); an embedded Resource script without `@tool` of its own that extends a tool script file is not screened, because the closure does not follow paths inside embedded sources (the same holds for a text scene whose embedded script reaches `@tool` only through an extended file and sits on a Resource rather than a node); and the text screen is a coarse heuristic: a `.tscn`/`.tres` with any GDScript `sub_resource` and the substring `@tool` anywhere is refused, which costs only the opt-in. A script that only extends a `@tool` script file gets a placeholder instance in the editor (its base `_init` does not run); it is still refused without the opt-in. `uid://` references in scripts are followed through `ResourceUID` (an unregistered uid is skipped); in tests a `.uid` sidecar written after the editor started was not registered, so uid scenarios seed their files before launch.
- Preview omits animation, particles, skinning, gameplay and WorldEnvironment.
- Editor camera is readable; framing uses the separate preview camera. Focus selects/switches workspace without moving the camera.
- Editor-play debugging: logs (`game logs --mode editor`) and live node inspection (`runtime.*`) work through the `GodotBridgeRuntime` autoload, which the plugin adds to `project.godot` (inert in exports and managed runs). Breakpoints, stack, variables (with array/dictionary/object drill-down), stepping and pause work over the same channel (no DAP, no `evaluate`); see "Debugger findings".
- Runtime trees are capped at 5,000 nodes (10,000 overflowed the debugger channel); requests time out after 5 s; with several simultaneously played instances the first active session answers. Editor log ring holds 5,000 entries, the game queues 2,000 between frames.
- Execution control uses undocumented engine command names (isolated in `ENGINE_COMMANDS`, covered by tests). `debug.variables` browses arrays, packed arrays, dictionaries and objects by path (paged, optional inlining); values of other types are encoded when the codec knows them, else marked unsupported with a `repr`. Object properties with a custom getter are never read (`unread`), and the hook methods `_get`, `_get_property_list` and `_validate_property` are never called: hooked objects are listed from ClassDB and the script API with a `hooks` flag on the summary, so properties those hooks add are not listed and the list can differ from the live one. Inner-class fields are readable when the owning script is found among the loaded scripts (roots, scene tree, stack frames, cached global classes, their preloads); otherwise they are `unread` with a "script source unavailable" reason. The getter scan of an owner file is conservative by name, and the owner search runs once per request. A script that is not GDScript (C#) cannot be checked and counts as hooked and its script variables are `unread`; that path is not tested (no Mono project in the tests), and a hooked native property that ClassDB lists but cannot read comes back as a null value rather than `unread`. Replies are capped at 500 entries. Breakpoints set in the script editor before the plugin loaded are not listed (they are still hit).
- Godot's own debug adapter (default 127.0.0.1:6006) is unauthenticated; it is documented in security.md and not used.
- Managed runtime uses a custom SceneTree and isolated user://; custom-main-loop projects should use editor mode.
- Current scene discovery requires the plugin and a saved scene; main/explicit scene runs work offline through supported engine APIs. `game run --current` on an unsaved scene is `SCENE_NOT_FOUND` in both modes (no scene open: `SCENE_NOT_OPEN`), and a rejected run never stops a running editor game. A scene given together with `--current` is resolved differently by mode (editor mode lets the scene win, managed mode lets `--current` win); no engine test covers the no-scene-open case, which a headless editor cannot reproduce.
- Stale-owner takeover judges the owner by a handshake probe with an unmatchable token (`owner-probe`): 300 ms to connect and send, 1 s for the reply. The first version gave the reply 300 ms; the repair raised it to 1 s and `poll()` now flushes the `AUTHENTICATION_FAILED` rejection in the frame that reads it. An unrelated service on a recycled port (silent, closing, speaking HTTP) is therefore stale. Accepted limits: an owner whose main loop runs no frame within 1 s, or that is already at eight clients, is taken over (the displaced owner's `maintain()` sees the foreign token and stops: newest editor wins); a foreign GodotBridge on the port counts as alive and fails closed; the editor's main thread blocks up to 1.3 s per start attempt against a silent stale listener. A live owner probed in the middle of a long operation is covered by manual verification only (the stock addon has no clean slow operation; the probe avoids the previous token, which would queue behind `busy`).
- A request still running after 120 s (`REQUEST_WATCHDOG_MS`) is answered `TIMEOUT` and the editor serves the next request; the abandoned operation may still run its side effects, so clients must treat `TIMEOUT` as an unknown outcome, and a handler script error is answered `INTERNAL_ERROR` with an unknown outcome too. The queue is effectively capped at eight entries (one pending request per client, eight clients), so the 32-entry `MAX_QUEUE` check and its `EDITOR_BUSY` answer are unreachable in practice; they were left in place.
- Managed-game integration tests are flaky on this machine: four managed-game tests failed in one graphical run (never diagnosed), and failures reproduced in combined headless runs (4 of 6 in one session), with or without the new tests. A plausible cause, not verified, is a Windows sharing race on `game/status.json` between `process_manager.atomic_json` (`Path.replace`, every 0.2 s in the supervisor) and `status()` (`read_text`, polled every 0.1 s), because Python's `open()` does not set `FILE_SHARE_DELETE`; one failure was a `PermissionError` reading that file inside `status()`. If the same race hit the supervisor it would mark the run failed, and a failing final write could leave `run.lock` behind, which would explain an `EDITOR_BUSY` cascade afterwards. To confirm, read the `error` field of the leftover `status.json` of a failing run.
- On this machine plain `pytest tests/unit` fails with a `%TEMP%` `PermissionError`: pass `--basetemp .artifacts/<name>` (and `-p no:cacheprovider`); `scripts/run_integration_tests.py` already sets `--basetemp`.
- Abandoned captures and crash-stale supervisor locks need explicit cleanup; stored PIDs are never killed.

## Debugger findings (Godot 4.7.2, empirical)

Why not the editor's Debug Adapter (DAP): its server runs by default in graphical and headless editors on 127.0.0.1:6006 (`network/debug_adapter/remote_port`), unauthenticated. A stateless connect-request-disconnect client keeps the game running and its breakpoints persist, but after any client has requested `scopes`/`variables`/`evaluate` (or stepped), later connections get an empty `stackTrace`, and `stepIn`/`stepOut` could leave a connection unanswered. The bridge uses its own authenticated channel and never talks to DAP.

What the DAP-free design relies on, all verified here:

- `EditorDebuggerSession.set_breakpoint` makes a running game break; with no active session it is not applied to the next run, so the bridge keeps a registry and applies it when the session starts. Bridge-set breakpoints do not trigger `_breakpoint_set_in_tree`.
- Debugger captures are serviced while the game is stopped, and `Engine.capture_script_backtraces(true)` called from the handler shows the stopped script's frames, locals and members beneath the handler's own frames.
- Engine commands `continue`, `next`, `step`, `out`, `break` work through `EditorDebuggerSession.send_message`. `break` stops between frames with no script frames (the next `step` in stops in game code); sending it while the game was still starting up crashed the editor, so the bridge pings the game first.
